# Как участвовать в проекте

Спасибо за интерес к курсу! Ниже — короткая версия правил: подробный протокол для людей
и агентов лежит в [`AGENTS.md`](AGENTS.md).

## Подготовка окружения

```bash
git clone https://github.com/ignatus4405-glitch/git_guide.git
cd git_guide
python3 --version                 # нужен 3.10+
python3 build.py                  # собрать сайт в ./site
python3 tools/serve.py --port 8000
```

Зависимостей нет — только стандартная библиотека Python. Если вы хотите включить локальные
проверки перед коммитом:

```bash
pipx install pre-commit
pre-commit install
```

## Что можно улучшить

- исправить опечатку, неточность или устаревшую команду в уроке;
- добавить пример, схему или вопрос самопроверки;
- предложить новый урок, страницу материалов или целый модуль;
- улучшить генератор (`tools/`), стили (`assets/css/site.css`) или workflow;
- предложить проверку в `tools/validate.py`, которая поймает будущие ошибки.

Идеи и найденные ошибки удобно оформлять через issue — шаблоны уже настроены.

## Правила изменений

1. **Одна задача — одна ветка.** Имя ветки: `feat/…`, `fix/…`, `docs/…`, `chore/…`.
2. **Перед PR обязательны проверки:**

   ```bash
   python3 build.py
   python3 tools/validate.py --site site --strict
   python3 tools/test_build.py
   ```

3. **Сообщения коммитов** — в формате Conventional Commits: `docs: уточнить описание rebase`.
4. **Контент** — по [`docs/CONTENT_GUIDE.md`](docs/CONTENT_GUIDE.md): front matter, минимум 400 слов,
   блок кода, вопрос самопроверки, ссылки через `lesson:` / `page:` / `module:`.
5. **Журнал** — добавьте запись в [`docs/CHANGELOG.md`](docs/CHANGELOG.md).
6. **Не коммитьте** каталог `site/`, файлы `docs/STATE.md` и `docs/MANIFEST.json` вручную:
   они генерируются.

## Процесс

1. Форкните репозиторий (или создайте ветку, если у вас есть права).
2. Сделайте изменения и прогоните проверки из раздела выше.
3. Откройте Pull Request: заполните шаблон, приложите скриншот для изменений интерфейса.
4. Дождитесь зелёных проверок CI: `validate`, `test`, `build`, `summary`.
5. После ревью PR сливается squash-слиянием, ветка удаляется.

## Что проверяет CI

| Job | Команда | Смысл |
| --- | --- | --- |
| `validate` | `python3 tools/validate.py --strict` | front matter, объём уроков, квизы, ссылки, запрет TODO |
| `test` | `python3 tools/test_build.py` | контракты генератора и полный цикл сборки |
| `build` | `python3 build.py` + `validate.py --site site` | сборка сайта и проверка внутренних ссылок |
| `summary` | — | сводка: прогон считается успешным только если всё выше зелёное |

## Кодекс общения

- Обсуждайте изменения и код, а не людей.
- Аргументируйте замечания: «почему» важнее «как правильно».
- Объясняйте причины в описании PR — это ускоряет ревью.
- Уважайте время ревьюеров: маленькие PR, понятные заголовки.

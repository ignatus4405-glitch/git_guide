## Issue: минимальная единица работы

Issue — это задача, баг или идея. Формулировка определяет, сколько времени уйдёт на уточнения.

```markdown title="Шаблон бага: структура, которая экономит время"
**Шаги воспроизведения**
1. Открыть страницу курса на узком экране (400 px)
2. Нажать «Поиск»
3. Ввести «rebase»

**Ожидаемое поведение**
Список результатов виден и прокручивается.

**Фактическое поведение**
Панель поиска выходит за границы экрана, результаты не видны.

**Окружение**
Chrome 128, macOS 15, ветка main@1a2b3c4
```

Правило хорошей задачи: **воспроизводимость**. Если задачу нельзя воспроизвести или проверить,
она превратится в переписку на десять комментариев.

## Метки, milestones, назначения

| Инструмент | Для чего | Пример |
| --- | --- | --- |
| Labels | классификация | `bug`, `docs`, `good first issue`, `blocked` |
| Milestone | привязка к релизу | `v1.1.0` |
| Assignees | кто делает | один ответственный, не трое |
| Projects | планирование (канбан) | колонки: Backlog → In progress → Review → Done |
| Linked PR | связь с изменениями | `Closes #42` в описании PR |

```bash title="Issues и метки из терминала"
gh issue create --title "Баг: поиск не работает на узком экране" \
  --body-file .github/ISSUE_TEMPLATE/bug_report.md \
  --label bug --label "good first issue"

gh issue list --label bug --assignee "@me" --state open
gh issue develop 42 --checkout        # создать ветку, связанную с issue
gh label create "good first issue" --color 7057ff --description "Подходит новичкам"
```

::: tip Метки как договор
Ограничьте набор меток 8–12 штуками и опишите их в `CONTRIBUTING.md`. Разрастающийся список
меток — сигнал, что процесс не определён: люди не знают, что ставить.
:::

## Шаблоны: правила по умолчанию

GitHub подставляет шаблоны из каталога `.github/`:

```text title="Структура"
.github/
├── ISSUE_TEMPLATE/
│   ├── bug_report.md
│   ├── feature_request.md
│   └── config.yml          # ссылки «не вопрос ли это?», запрет пустых issue
├── PULL_REQUEST_TEMPLATE.md
└── CODEOWNERS
CONTRIBUTING.md             # как поднять проект, как тестировать, что ожидается от PR
```

```yaml title=".github/ISSUE_TEMPLATE/bug_report.md (front matter шаблона)"
---
name: Сообщение об ошибке
about: Что-то работает не так, как ожидалось
title: "[bug]: "
labels: ["bug", "triage"]
assignees: []
---
```

::: warning Пустой шаблон вреден
Шаблон, который никто не заполняет, учит игнорировать форматы. Оставьте в нём три-четыре
обязательных вопроса, добавьте `config.yml` с `blank_issues_enabled: false` — тогда issue
без структуры не создаются.
:::

## Процесс: от задачи до релиза

```text title="Цепочка работы"
Issue → ветка → PR (Closes #42) → ревью → слияние → релиз
   ↑                                            ↓
   └───────── автоматизация: Actions, Projects, уведомления ─────────┘
```

Автоматизировать можно почти всё:

- Actions добавляет метку `triage` новым issue или приветствует контрибьютора;
- при открытии PR автоматически запрашивается ревью у `CODEOWNERS`;
- при слиянии PR в `main` закрываются связанные issue и создаётся черновик релиза;
- Projects автоматически переводит карточку в колонку по событию.

```yaml title=".github/workflows/label-new-issues.yml — авторазметка новых issue"
name: Разметка новых issue
on:
  issues:
    types: [opened]
permissions:
  issues: write
jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - run: gh issue edit "${{ github.event.issue.number }}" --add-label triage
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GH_REPO: ${{ github.repository }}
```

## Триаж: как список задач перестаёт расти бесконечно

Раз в неделю команда проходит по новым issue и отвечает на четыре вопроса:

| Вопрос | Варианты ответа | Что делать |
| --- | --- | --- |
| Это воспроизводится? | да / нет | без воспроизведения — запросить детали, добавить метку `needs info` |
| Это точно проблема? | да / не проблема | если ожидаемое поведение — закрыть с объяснением |
| Насколько срочно? | блокер / важно / потом | блокеры идут в текущий milestone, «потом» — в backlog |
| Кто возьмётся? | конкретный человек | без ответственного задача живёт месяцами |

Жёсткое правило: **у задачи есть либо исполнитель, либо дата, либо причина ждать**.
Иначе backlog превращается в свалку, которую никто не читает.

```bash title="Массовые операции при триаже"
gh issue list --state open --limit 100 --json number,title,labels \
  --jq '.[] | select(.labels | length == 0) | "#\(.number) \(.title)"'
gh issue edit 42 --add-label "priority: high" --milestone v1.1.0
gh issue close 17 --reason "not planned" --comment "Ожидаемое поведение: описано в документации."
```

## Связь задач с релизами

Полезная привычка: у каждого релиза — свой milestone, и в него попадает только то,
что точно будет сделано к дате. По закрытию milestone собирается changelog:

```bash title="Что вошло в релиз"
gh issue list --milestone v1.1.0 --state closed --json number,title \
  --jq '.[] | "- #\(.number) \(.title)"' > RELEASE_NOTES.md
```

Так список изменений релиза формируется из фактов проекта, а не из памяти разработчика.

## Итоги

- Хорошая issue воспроизводима и проверяема — иначе задача не готова к работе.
- Метки, milestones и Projects превращают список задач в понятный поток.
- Шаблоны `.github/` и `CONTRIBUTING.md` делают правила поведением по умолчанию.
- Автоматизация (Actions, Projects, ссылки `Closes #N`) убирает ручные шаги процесса.
- Минимум меток и максимум ясности лучше сложной, но всеми игнорируемой схемы.

::: exercise Упражнение: настроить процесс в своём репозитории
1. Создайте три метки: `bug`, `docs`, `good first issue`.
2. Добавьте шаблоны `bug_report.md` и `feature_request.md` в `.github/ISSUE_TEMPLATE/` и `config.yml`.
3. Напишите короткий `CONTRIBUTING.md`: как запустить проект, как проверить изменения, что ожидается в PR.
4. Заведите issue через `gh issue create` по своему же шаблону, затем создайте связанную ветку:
   `gh issue develop <номер> --checkout`.
5. Сделайте коммит, откройте PR с `Closes #<номер>` и проверьте, что issue закрылся после слияния.
:::

::: quiz Зачем в шаблоне issue требовать «шаги воспроизведения»?
- ( ) Чтобы issue выглядели одинаково и аккуратно смотрелись в списке
- (x) Чтобы задачу можно было воспроизвести и проверить исправление
- ( ) Чтобы автоматически назначать метку bug

Воспроизводимость — главное свойство задачи, которую можно взять в работу: без неё
непонятно, что именно чинить и как убедиться, что починили.
:::

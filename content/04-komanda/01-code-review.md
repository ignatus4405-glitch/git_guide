## Зачем нужно ревью

Ревью решает три задачи: находит дефекты до продакшена, распространяет знание о коде
и создаёт точку обсуждения решений. Оно **не** решает задачу «поймать человека на ошибке» —
и именно поэтому тон замечаний критичен для скорости работы команды.

## Как готовить PR к ревью

Автор влияет на скорость ревью сильнее, чем ревьюер:

- **Одна задача — один PR.** Правки «по пути» разносят обсуждение и усложняют откат.
- **Описание важнее диффа.** Что сделано, зачем, как проверить, что осталось за рамками.
- **Зелёный CI до запроса ревью.** Ревьюер не должен угадывать, работает ли код.
- **Самопроверка.** Пройдите дифф глазами: лишние `console.log`, отладочные строки, забытые файлы.
- **Ссылка на задачу.** Issue даёт контекст, которого нет в коде.

## Чек-лист ревьюера

```text title="Порядок просмотра (15 минут)"
1. Описание PR и связанная задача      → правильно ли решается нужная проблема
2. Тесты и проверки                     → что гарантировано, что нет
3. Дифф по файлам от «сложного» к простому
4. Секреты, логи, отладочный код        → не утекли ли ключи/данные
5. Обработка ошибок и крайние случаи    → что будет при пустом ответе, таймауте, отказе
6. Производительность и зависимости     → не тянем ли лишнее
7. Документация и changelog             → поймёт ли следующий человек
```

Практика: сначала читайте описание и тесты, только потом сам код — это даёт рамку понимания,
без которой дифф кажется набором случайностей.

## Как писать замечания

| Категория | Пример формулировки |
| --- | --- |
| Блокирующее (`[blocker]`) | «Здесь теряется код ошибки: при таймауте вернётся `null`. Предлагаю пробросить исключение.» |
| Вопрос | «Почему выбран `ttl=60`? Если есть расчёт или замер — добавьте, пожалуйста, комментарий.» |
| Предложение (`[nit]`) | «[nit] Можно `dict.setdefault`, но и текущий вариант читается нормально — на ваше усмотрение.» |
| Похвала | «Отличные тесты на граничные случаи — как раз то, чего не хватало.» |

Правила тона:

- комментируйте код, а не человека: «эта функция теряет ошибку», а не «вы снова не обработали ошибку»;
- объясняйте причину: замечание с обоснованием почти всегда принимается;
- отделяйте обязательное от вкусового: префиксы `[blocker]` и `[nit]` экономят споры;
- если не уверены — задайте вопрос, а не требуйте.

::: warning Антипаттерн: «Сделай вот так» без обоснования
Ревьюер не должен диктовать стиль там, где нет объективного критерия. Если требование
важно для проекта — оно должно попасть в линтер или в документацию, а не в комментарии PR.
:::

## CODEOWNERS: ревью приходит само

Файл `.github/CODEOWNERS` определяет, кого GitHub автоматически добавит ревьюером для
изменённых путей. В связке с branch protection (Require review from Code Owners) это делает
правило обязательным, а не рекомендательным.

```text title=".github/CODEOWNERS"
# По умолчанию — все владельцы репозитория
*                       @org/maintainers

# Конкретные области
/tools/                 @org/build-team
/docs/                  @org/writers
/.github/workflows/     @org/ci-owners
*.md                    @org/writers
```

::: tip CODEOWNERS и «бутылочное горлышко»
Если один человек владеет всем кодом, он становится единственной точкой отказа.
Для небольших команд лучше указывать команду (`@org/build-team`), чтобы ревью мог сделать любой участник.
:::

## Автоматизация там, где возможно

Часть проверок не должна зависеть от внимательности ревьюера:

| Проверка | Инструмент | Что закрывает |
| --- | --- | --- |
| Форматирование и стиль | formatters, линтеры в pre-commit | споры о пробелах и кавычках |
| Тесты и сборка | GitHub Actions (модуль 5) | регрессии |
| Типы и статический анализ | mypy/tsc/CodeQL | целый класс ошибок |
| Секреты | secret scanning + push protection | утечки ключей |
| Зависимости | Dependabot | уязвимые версии |
| Правописание и ссылки | отдельный job | «мелкие» ошибки в документации |

## Итоги

- Ревью — про код и решения, а не про людей; цель — качество и общее понимание.
- Автор управляет скоростью: маленький PR, понятное описание, зелёный CI.
- Замечания делятся на блокирующие и необязательные, и это явно помечается.
- `CODEOWNERS` + branch protection автоматизируют маршрутизацию ревью.
- Всё, что можно проверить машиной, отдайте линтерам и CI.

::: exercise Упражнение: провести ревью
1. Возьмите любой свой старый PR или создайте учебный с правкой в 20–40 строк.
2. Пройдите чек-лист ревьюера и выпишите замечания, разделив их на `[blocker]` и `[nit]`.
3. Сформулируйте каждое замечание так, чтобы в нём было условие и объяснение причины.
4. Добавьте в репозиторий `.github/CODEOWNERS` и шаблон PR из этого урока.
5. Сделайте так, чтобы правило «Require review from Code Owners» было включено для `main`.
:::

::: quiz Ревьюер нашёл проблему в 400-строчном PR и просит переделать половину. Что делать быстрее всего?
- ( ) Спорить в комментариях до победного — принцип важнее
- (x) Согласовать минимальный объём для слияния, остальное вынести в отдельный PR
- ( ) Слить PR самому через admin-права

Большие PR почти всегда содержат смешанные задачи: часть можно слить сразу, а спорные
изменения вынести в отдельный PR и обсудить предметно. Это быстрее для всех и не блокирует задачу.
:::

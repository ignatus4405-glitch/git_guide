## Семантическое версионирование

Формат `MAJOR.MINOR.PATCH` (например, `2.4.1`) с чёткими правилами:

| Часть | Когда увеличивается | Пример |
| --- | --- | --- |
| MAJOR | несовместимое изменение API | удалили функцию `sendOld()` |
| MINOR | новая функциональность без поломок | добавили параметр со значением по умолчанию |
| PATCH | исправление без изменения поведения | исправили ошибку в расчёте |

Дополнительно: предварительные версии (`1.0.0-rc.1`, `2.0.0-beta.3`) и метаданные сборки (`1.2.3+build.7`).
Для библиотек важно фиксировать, что именно считается публичным API: без этого semver превращается
в произвольные цифры.

## Теги: два вида

```bash title="Создание тегов"
git tag -a v1.2.0 -m "Релиз 1.2.0: экспорт отчётов"     # аннотированный (рекомендуется)
git tag v1.2.0-hotfix                                  # лёгкий (просто указатель)
git tag -l "v1.*"                                      # список
git show v1.2.0                                        # содержимое аннотированного тега
git push origin v1.2.0                                 # теги не уходят при обычном push!
git push --tags                                        # все теги

git tag -d v1.2.0                                      # удалить локально
git push origin :refs/tags/v1.2.0                      # удалить на сервере
```

| Вид | Что хранит | Когда использовать |
| --- | --- | --- |
| Лёгкий | только SHA | временные метки, локальные проверки |
| Аннотированный | SHA + автор + дата + сообщение | релизы: подписывается, содержит смысл |

::: tip Теги не летят вместе с веткой
`git push` отправляет коммиты ветки, но не теги. Публикация тега — отдельное действие:
`git push origin v1.2.0` или `--tags`. Если этого не сделать, релиз на GitHub создать не получится.
:::

## GitHub Releases

Release — это тег плюс описание, список изменений и файлы для скачивания. Это то, что видят
пользователи, в отличие от «просто тега» в `git tag`.

```bash title="Релиз из терминала"
gh release create v1.2.0 --title "1.2.0 — экспорт отчётов" \
  --notes-file RELEASE_NOTES.md \
  --asset build/report.zip \
  --generate-notes           # если хочется автоматический список изменений

gh release list
gh release view v1.2.0 --web
gh release delete v1.2.0 --cleanup-tag
```

## Автоматизация: релиз по тегу

```yaml title=".github/workflows/release.yml"
name: Релиз

on:
  push:
    tags: ["v*.*.*"]           # запускается только при публикации тега

permissions:
  contents: write              # создать релиз

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0       # нужна история, чтобы построить changelog
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - name: Тесты и сборка
        run: |
          python3 tools/test_build.py
          python3 build.py
      - name: Архив для скачивания
        run: tar -czf git-guide-${GITHUB_REF_NAME}.tar.gz site
      - name: Создать релиз
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh release create "${GITHUB_REF_NAME}" \
            --title "${GITHUB_REF_NAME}" \
            --generate-notes \
            "git-guide-${GITHUB_REF_NAME}.tar.gz"
```

Как это работает по шагам:

1. Вы сливаете изменения в `main` и создаёте тег: `git tag -a v1.1.0 -m "..." && git push origin v1.1.0`.
2. По push тега запускается workflow (триггер `tags: ["v*.*.*"]`).
3. Job проверяет код, собирает артефакт и создаёт релиз с автоматическими заметками.
4. `--generate-notes` формирует список изменений из коммитов и ранее слитых PR.

::: warning Версия должна быть в одном месте
Если версия лежит и в `site.yml`, и в теге, и в `package.json`, они неизбежно разойдутся.
Выберите источник истины (обычно тег) и подставляйте его в сборку: например,
`${GITHUB_REF_NAME}` в workflow или `python3 build.py --version $GITHUB_REF_NAME`.
:::

## Changelog, который не устаревает

Три уровня автоматизации:

| Уровень | Как делается | Плюсы/минусы |
| --- | --- | --- |
| Автоматический | `--generate-notes` из коммитов и PR | бесплатно, но качество зависит от сообщений |
| Полуавтоматический | Conventional Commits + `release-drafter` или `semantic-release` | группировка по типам, нужен формат коммитов |
| Ручной | файл `CHANGELOG.md` в формате Keep a Changelog | полный контроль, легко забыть |

В этом курсе используется комбинированный подход: изменения описываются руками в
`docs/CHANGELOG.md`, а версия курса фиксируется в `site.yml` и в описании релиза.

```markdown title="Формат записи (Keep a Changelog)"
## [1.1.0] — 2026-10-15
### Добавлено
- Модуль «Продвинутые приёмы»: 3 урока про хуки, большие файлы и релизы.
### Исправлено
- Проверка якорей в валидаторе больше не считается только по заголовкам H2.
```

## Итоги

- Semver: MAJOR — несовместимость, MINOR — новая функциональность, PATCH — исправление.
- Аннотированные теги несут смысл и подпись; лёгкие годятся только для временных меток.
- Теги публикуются отдельно (`git push origin <tag>`), иначе релиз не создать.
- Release = тег + описание + артефакты; автоматизируется по триггеру `push: tags`.
- Источник истины о версии должен быть один; changelog обновляйте в одном процессе с релизом.

::: exercise Упражнение: выпустить релиз
1. В своём репозитории добавьте workflow `release.yml` с триггером `tags: ["v*.*.*"]`.
2. Создайте аннотированный тег `v0.1.0` и запушьте его — workflow должен создаться сам.
3. Убедитесь, что релиз появился со списком изменений и прикреплённым архивом.
4. Добавьте в репозиторий `CHANGELOG.md` и опишите версии `0.1.0` и `0.2.0` в формате Keep a Changelog.
5. Сделайте так, чтобы версия в `site.yml` совпадала с тегом: сравните их в шаге workflow
   и уроните сборку при расхождении.
:::

::: quiz Вы создали тег локально и запушили ветку. Почему релиз не появился?
- ( ) GitHub создаёт релизы только в веб-интерфейсе
- (x) Теги не отправляются обычным `git push` — нужен push тега или --tags
- ( ) Workflow не настроен на событие `release`

`git push` публикует коммиты ветки. Теги отправляются отдельной командой
(`git push origin <tag>` или `git push --tags`) — только тогда сработает триггер `push: tags`.
:::

## Почему большие файлы — проблема

Git хранит **каждую версию** файла. Текстовый файл на 10 КБ после 200 правок занимает
примерно 200 × 10 КБ минус сжатие, а бинарник на 50 МБ, изменённый 10 раз, даст ~500 МБ,
которые скачает каждый при клонировании — навсегда.

Порог, за которым стоит остановиться и подумать: **файлы больше 10 МБ и растущие бинарные
артефакты**. GitHub отклоняет отдельные файлы больше 100 МБ и предупреждает после 50 МБ.

## Git LFS: содержимое — снаружи

LFS (Large File Storage) заменяет файл маленьким указателем, а сам файл загружает в отдельное
хранилище.

```bash title="Установка и настройка"
git lfs install                               # один раз на машине
git lfs track "*.psd" "*.mp4" "assets/audio/*"  # создаёт .gitattributes
git add .gitattributes && git commit -m "chore: включить LFS для бинарных ассетов"
git lfs ls-files                              # какие файлы под LFS
git lfs status
```

| Плюс | Минус |
| --- | --- |
| Клонирование лёгкое: скачиваются только указатели | нужен доступ к хранилищу LFS (своё или GitHub) |
| История не раздувается | квоты: на GitHub бесплатный лимит 1 ГБ хранения и 1 ГБ трафика в месяц |
| Работает прозрачно для обычных команд | в старых версиях и сторонних CI — дополнительная настройка |

## Подмодули: чужой репозиторий внутри вашего

```bash title="Добавление и клонирование"
git submodule add https://github.com/OWNER/LIB.git vendor/lib
git commit -m "chore: подключить vendor/lib как подмодуль"
cat .gitmodules                               # где лежит описание

# клонирование проекта с подмодулями
git clone --recurse-submodules git@github.com:OWNER/REPO.git
# если забыли — потом:
git submodule update --init --recursive

git submodule update --remote vendor/lib      # перевести на новый коммит зависимости
```

Ключевой момент: родительский репозиторий хранит **не содержимое**, а конкретный коммит
подмодуля. Поэтому «обновление зависимости» — это коммит, меняющий её SHA: изменение
видно в ревью и откатывается вместе с остальным кодом.

::: warning Подмодули и участники команды
Забытый `git submodule update --init` — источник ошибок «файлы есть, а содержимого нет».
Если проект сложный, часто проще использовать менеджер пакетов (npm, pip, go modules). У подмодулей
есть смысл, когда нужен именно репозиторий с собственной историей: например, общая конфигурация CI.
:::

## Быстрые клоны: depth, filter, sparse-checkout

```bash title="Экономия времени и места"
git clone --depth 1 https://github.com/OWNER/BIG.git        # только последний коммит
git clone --filter=blob:none --no-checkout https://...      # без содержимого файлов
git clone --filter=tree:0 https://...                       # без деревьев и блобов

# работать только с частью дерева (монорепозиторий)
git sparse-checkout init --cone
git sparse-checkout set apps/web tools
git sparse-checkout list
git sparse-checkout disable
```

| Команда | Что скачивает | Когда полезна |
| --- | --- | --- |
| `--depth 1` | один коммит | CI, лёгкая сборка без истории |
| `--filter=blob:none` | деревья и коммиты, файлы — по требованию | монорепозитории, работа «в одном подкаталоге» |
| `--filter=tree:0` | минимум объектов | скрипты, где нужна только пара файлов |
| `--single-branch` | только одну ветку | клоны «под задачу» |

::: note Комбинация даёт максимум
`git clone --filter=blob:none --sparse <url> && git sparse-checkout set tools/` даёт и быстрый клон,
и локально только нужный каталог. Git подгружает файлы при обращении к ним.
:::

## Если репозиторий уже раздут

```bash title="Диагностика и уменьшение"
git count-objects -vH                       # размер объектов и паков
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" && $3>5000000 {print $3, $4}' | sort -rn | head   # крупные блобы
git gc --aggressive --prune=now             # переупаковка (локально, не помогает с историей)
```

Удалить большой файл из истории можно через `git filter-repo` (см. модуль «Безопасность»):

```bash title="Удаление крупного файла из истории"
git clone --mirror git@github.com:OWNER/REPO.git repo.git
cd repo.git
git filter-repo --invert-paths --path assets/video/demo.mp4
git push --force --all && git push --force --tags
```

После такой операции рекомендуется настроить LFS или перенести файлы в релизные артефакты,
иначе файл вернётся в репозиторий с очередным коммитом.

## Итоги

- Большие и часто меняющиеся бинарные файлы — главная причина «тяжёлых» репозиториев.
- LFS выносит содержимое наружу, оставляя в Git указатели; следите за квотами.
- Подмодуль фиксирует чужой репозиторий на конкретном коммите — это часть ревью.
- Частичные клоны и sparse-checkout ускоряют работу с большими монорепозиториями.
- Историю можно почистить (`filter-repo`), но лучше предотвращать попадание файлов.

::: exercise Упражнение: ускорить клон
1. Возьмите большой публичный репозиторий (например, `torvalds/linux` — только для замеров).
2. Замерьте время и размер: `git clone --depth 1` и обычный клон.
3. Сделайте клон с `--filter=blob:none --sparse`, затем `git sparse-checkout set Documentation`.
4. Сравните `du -sh .git` для трёх вариантов и объясните разницу.
5. Создайте свой репозиторий с LFS-файлом, сделайте три версии файла и проверьте,
   что `.git` не растёт пропорционально размеру файла (`git count-objects -vH`).
:::

::: quiz Что хранит родительский репозиторий, если подключён подмодуль?
- ( ) Полную копию содержимого подмодуля
- (x) Ссылку на конкретный коммит подмодуля и адрес в .gitmodules
- ( ) Только имя каталога, содержимое всегда подтягивается с ветки main

В индексе родителя подмодуль — это «gitlink»: конкретный SHA коммита. Поэтому обновление
зависимости фиксируется отдельным изменением и видно в истории.
:::

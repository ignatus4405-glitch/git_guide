## Что физически лежит в .git

```text title="Каталог .git"
HEAD                 # куда указывает текущая ветка
config               # настройки репозитория
description          # используется только серверными хуками
index                # область подготовки (двоичный файл)
objects/             # все объекты: блобы, деревья, коммиты, теги
refs/heads/          # ветки: имя файла → SHA коммита
refs/tags/           # теги
packed-refs          # ссылки, упакованные в один файл
logs/                # reflog: журнал перемещений ссылок
```

Ветка — это файл размером 41 байт со SHA внутри. Именно поэтому создание ветки мгновенно.

## Четыре типа объектов

![Схема: связи коммита, дерева и блобов](assets/img/diagrams/commit-internals.svg "Коммит → дерево → блобы: базовые объекты Git")

| Тип | Что содержит | Пример |
| --- | --- | --- |
| `blob` | содержимое файла (без имени) | текст `README.md` |
| `tree` | список записей: режим, тип, SHA, имя | каталог |
| `commit` | ссылку на tree, родителей, автора, сообщение | один коммит |
| `tag` | ссылку на объект, автора тега, сообщение | аннотированный тег |

```bash title="Разбор вручную"
git hash-object -w README.md            # записать блоб, получить SHA
git cat-file -t <sha>                   # тип объекта: blob/tree/commit/tag
git cat-file -p <sha>                   # содержимое объекта
git cat-file -s <sha>                   # размер в байтах

git ls-tree HEAD                        # дерево коммита
git ls-tree -r HEAD                     # рекурсивно: все файлы
git rev-parse HEAD                      # SHA коммита
git rev-parse HEAD^{tree}               # SHA дерева
git rev-parse HEAD:README.md            # SHA блоба конкретного файла
```

Смысл в том, что **имя файла хранится не в блобе, а в дереве**: одинаковое содержимое в двух
каталогах — один объект и один SHA. Так Git экономит место без дополнительной логики.

## Ключевая формула

```text title="Как получается SHA"
blob   = sha1("blob <размер>\0" + содержимое)
tree   = sha1("tree <размер>\0" + записи)
commit = sha1("commit <размер>\0" + заголовки + сообщение)
```

Отсюда два важных следствия:

- содержимое неизменяемо: изменить коммит «на месте» нельзя, не изменив SHA;
- одинаковое содержимое в разных репозиториях имеет один и тот же SHA — поэтому возможна
  эффективная синхронизация: сервер и клиент обмениваются только отсутствующими объектами.

::: warning MD5 в описании? Нет, SHA-1
Git исторически использует SHA-1 с защитой от коллизий; в современных версиях есть
экспериментальная поддержка SHA-256 (`git init --object-format=sha256`). Обновляться
на SHA-256 стоит взвешенно: совместимость с сервисами и инструментами пока не полная.
:::

## Упаковка: packfiles и дельты

Отдельные файлы объектов (`objects/ab/cdef...`) удобны, но занимают много места. `git gc`
(или автоматическая упаковка) собирает их в `.pack` и `.idx`, где похожие объекты хранятся
дельтами: например, версии одного файла — как разница между ними.

```bash title="Наблюдение за упаковкой"
git count-objects -vH          # сколько объектов и сколько места
ls -la .git/objects/pack/      # список pack-файлов
git gc --auto                  # автоматический сбор (Git делает это сам)
git gc --aggressive            # переупаковка с лучшим сжатием (долго)
git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n | tail -5   # крупнейшие объекты
```

::: tip Почему клон большого репозитория иногда быстрее, чем кажется
Git передаёт не «файлы», а упакованные дельты. Поэтому `git clone` проекта с миллионом
коммитов может занять меньше, чем выгрузка «одной актуальной версии» из архива.
:::

## Диагностика: когда что смотреть

| Симптом | Инструмент | Что показывает |
| --- | --- | --- |
| «Репозиторий раздут» | `git count-objects -vH`, `git verify-pack -v` | размер объектов, крупнейшие блобы |
| «История повреждена» | `git fsck --full` | битые, висячие и потерянные объекты |
| «Ссылка сломалась» | `git fsck --lost-found`, `git reflog` | объекты без ссылок, история перемещений |
| «Что реально улетит на сервер» | `git bundle create repo.bundle --all` | автономный перенос всей истории |
| «Кто изменил файл» | `git log --follow`, `git blame` | контекст изменений |

```bash title="Проверка здоровья репозитория"
git fsck --full --strict       # полная проверка целостности объектов
git fsck --lost-found          # записать потерянные объекты в .git/lost-found
git reflog --date=iso | head   # журнал перемещений с датами
```

## Перенос истории без сервера

```bash title="bundle: репозиторий в одном файле"
git bundle create backup-$(date +%F).bundle --all
git bundle verify backup-2026-10-15.bundle
git clone backup-2026-10-15.bundle repo-restored        # восстановление
git bundle create incremental.bundle main ^origin/main  # только новые коммиты
```

Это рабочий способ передать репозиторий в закрытую сеть или сделать резервную копию, не завися
от GitHub.

## Итоги

- `.git` — обычный каталог с объектами и ссылками; ветка — файл со SHA.
- Четыре типа объектов: blob, tree, commit, tag; имя файла живёт в дереве.
- SHA считается от типа, размера и содержимого — поэтому история неизменяема.
- Packfiles и дельты экономят место; `git gc` выполняется автоматически.
- `git cat-file`, `git fsck`, `git reflog` и `git bundle` — базовый набор для отладки и переноса.

::: exercise Упражнение: собрать коммит руками
1. Создайте пустой репозиторий (`git init plumbing-demo`) и перейдите в него.
2. Запишите блоб: `git hash-object -w --stdin <<< "привет"` — запомните SHA.
3. Создайте дерево через `git update-index --add --cacheinfo 100644,<sha>,hello.txt` и `git write-tree`.
4. Создайте коммит руками: `git commit-tree <tree-sha> -m "первый коммит"`, затем
   `git update-ref refs/heads/main <commit-sha>` и `git switch main`.
5. Проверьте результат: `git status`, `git log --stat`, `git cat-file -p HEAD`.
6. Сделайте `git bundle create demo.bundle --all`, удалите каталог и восстановите
   репозиторий из bundle в другом месте.
:::

::: quiz Почему одинаковое содержимое файла в двух каталогах хранится как один объект?
- ( ) Git сравнивает файлы и удаляет дубликаты при сборке мусора
- (x) SHA блоба зависит только от содержимого, поэтому оба дерева ссылаются на один объект
- ( ) Деревья хранят только имена файлов, а содержимое подгружается с сервера

Блоб адресуется хешем содержимого, а имена и структура — в деревьях. Поэтому дублирование
содержимого автоматически становится «ссылкой на тот же объект» без специальной логики.
:::

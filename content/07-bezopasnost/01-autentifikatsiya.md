## Карта способов аутентификации

![Схема: пять слоёв защиты репозитория](assets/img/diagrams/security-layers.svg "От аутентификации до процессов: чем правее, тем раньше ловится проблема")

| Способ | Где применяется | Плюсы | Минусы |
| --- | --- | --- | --- |
| SSH-ключ | ручная работа в терминале | не истекает, не требует копирования секрета | нужно настроить один раз на каждой машине |
| Fine-grained PAT | скрипты, локальная автоматизация | точные права на конкретные репозитории | истекает, нужно хранить |
| Classic PAT | старые интеграции | шире права | избыточные права (по умолчанию весь аккаунт) |
| GitHub App / installation token | сервисы и боты | короткоживущие токены, точные права | сложнее настроить |
| OIDC | CI, облака | секретов нет вообще | требует поддержки у провайдера |

::: warning Пароль от аккаунта
Пароль используется только для входа в веб-интерфейс. Для Git-операций по HTTPS нужен **токен**,
для SSH — ключ. С включённой двухфакторной аутентификацией это правило соблюдается автоматически.
:::

## SSH: один раз и навсегда

```bash title="Генерация и подключение"
ssh-keygen -t ed25519 -C "work@example.com"
# секретная часть остаётся в ~/.ssh/id_ed25519, публичная — в id_ed25519.pub
cat ~/.ssh/id_ed25519.pub      # → GitHub → Settings → SSH and GPG keys → New SSH key

ssh -T git@github.com          # проверка: Hi <user>! You've successfully authenticated
ssh-add -l                     # какие ключи загружены в агент
```

Несколько аккаунтов на одной машине удобно развести через `~/.ssh/config`:

```text title="~/.ssh/config"
Host github-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes

Host github-personal
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes
```

```bash title="Клонирование с нужным ключом"
git clone git@github-work:company/private-repo.git
# remote можно поправить и позже:
git remote set-url origin git@github-work:company/private-repo.git
```

## Fine-grained токены

Создаются в Settings → Developer settings → Personal access tokens → Fine-grained tokens.
Дают минимум прав: выбрать репозитории, затем конкретные разрешения.

```bash title="Использование токена"
export GH_TOKEN=github_pat_xxxxxxxxxxxx     # для gh CLI и API
gh auth status                              # покажет, какие права выданы

# для git по HTTPS в неинтерактивных сценариях:
git clone https://x-access-token:$GH_TOKEN@github.com/OWNER/REPO.git
```

Правила обращения с токеном:

- **срок жизни** — 30–90 дней, а не «бессрочно»;
- **минимум прав**: для чтения приватного репозитория достаточно `Contents: read`;
- **не в репозиторий**: только в переменные окружения, менеджер секретов или CI-секреты;
- **отзывать сразу**, как только задача, под которую он создавался, закрыта.

::: note Токен в URL — плохая практика
Команда выше с `x-access-token:$GH_TOKEN@...` сохранит токен в `.git/config` при клонировании
через HTTPS. Для локальной работы используйте SSH или credential helper, который хранит
секрет в защищённом хранилище системы.
:::

## Двухфакторная аутентификация

Включить обязательно (в некоторых организациях это требование для доступа к приватному коду):
Settings → Password and authentication → Two-factor authentication. Варианты:

| Вариант | Комментарий |
| --- | --- |
| TOTP-приложение | базовый и надёжный: 1Password, Google Authenticator, Aegis |
| Passkey / security key (WebAuthn) | самый устойчивый к фишингу |
| SMS | использовать только как временный вариант |

Сохраните резервные коды и добавьте второй фактор — потеря единственного устройства означает
потерю доступа к аккаунту, а восстановление может занять дни.

## Подпись коммитов

Подпись позволяет проверить, что коммит действительно создан вами. В интерфейсе GitHub такой
коммит помечается «Verified».

```bash title="Подпись через SSH-ключ (простой вариант)"
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
# публичную часть нужно добавить на GitHub как «Signing key» (отдельно от ключа аутентификации)
git log --show-signature -1
```

Для критичных проектов подпись коммитов включают в защиту ветки: тогда в `main` нельзя
запушить неподписанный коммит.

## Итоги

- Для ручной работы используйте SSH-ключ, для скриптов — fine-grained токен с коротким сроком.
- Несколько аккаунтов разводятся через `~/.ssh/config` с директивами `Host`.
- 2FA обязательна; предпочитайте passkey/security key, держите резервные коды отдельно.
- Токены не попадают в репозиторий и файлы конфигурации — только в окружение и CI-секреты.
- Подпись коммитов позволяет проверять авторство и включается в правила защиты веток.

::: exercise Упражнение: настроить безопасный доступ
1. Сгенерируйте новый SSH-ключ `id_ed25519_work` и добавьте его в `~/.ssh/config` под именем хоста `github-work`.
2. Проверьте доступ: `ssh -T git@github-work`.
3. Создайте fine-grained токен сроком на 30 дней с правами `Contents: read` на один репозиторий
   и проверьте его: `GH_TOKEN=... gh api repos/OWNER/REPO --jq .full_name`.
4. Включите 2FA и сохраните резервные коды в менеджере паролей.
5. Настройте подпись коммитов через SSH и убедитесь, что GitHub показывает «Verified».
:::

::: quiz Что произойдёт с доступом, если сгенерировать новый SSH-ключ и удалить старый публичный ключ из GitHub?
- ( ) Ничего: ключи кэшируются на сервере
- (x) Машины, где остался только старый ключ, потеряют доступ; новые ключи продолжат работать
- ( ) Все активные сессии будут немедленно разорваны, включая веб

Доступ по SSH определяется публичными ключами в аккаунте. Удалённый ключ перестаёт работать
сразу, поэтому обновлять ключи нужно на всех машинах, где они используются.
:::

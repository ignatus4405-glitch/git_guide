## Три инструмента, которые легко перепутать

| Инструмент | Что хранит | Видно в логах | Где использовать |
| --- | --- | --- | --- |
| `secrets.*` | пароли, токены, ключи | нет (маскируется) | подключение к внешним системам |
| `vars.*` | несекретные настройки: регион, URL, версия | да | параметры сборки |
| `GITHUB_TOKEN` | выдается автоматически на прогон | нет | работа с самим репозиторием |

```bash title="Управление из CLI"
gh secret set API_TOKEN --body "$(openssl rand -hex 24)"
gh secret list
gh variable set DEFAULT_REGION --body "eu-central-1"
gh secret set DB_PASSWORD --env production      # секрет конкретного окружения
```

## Окружения и подтверждения

Окружения (Settings → Environments) дают три возможности: свои секреты, ожидание одобрения
и ограничение по ветвям.

```yaml title="Деплой только после подтверждения"
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production          # в настройках: Required reviewers + Wait timer
      url: https://example.com
    steps:
      - name: Публикация
        env:
          TOKEN: ${{ secrets.PROD_TOKEN }}
        run: ./scripts/deploy.sh
```

Что это даёт:

- секрет `PROD_TOKEN` недоступен job-ам без окружения `production`;
- деплой ждёт одобрения конкретных людей, случайный прогон ничего не сломает;
- в истории видно, кто именно одобрил публикацию и когда.

::: tip Правило «одно окружение — один набор секретов»
Не используйте один токен для стенда и прода. Разные окружения с разными секретами —
это ещё и удобный способ отозвать доступ точечно.
:::

## OIDC: секретов нет вовсе

Долгоживущий токен облака — это риск: он не истекает, его копируют, он утекает. OIDC позволяет
получить короткоживущие креды прямо во время прогона.

```yaml title="Пример: обмен OIDC-токена на креды (AWS)"
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: eu-central-1
      - run: aws s3 sync site/ s3://my-bucket --delete
```

В облаке настраивается доверие только к вашему репозиторию и ветке: другой проект не сможет
воспользоваться ролью.

## Защита от утечек: три уровня

![Схема: слои безопасности — аутентификация, права, секреты, код, процесс](assets/img/diagrams/security-layers.svg "Чем раньше обнаружена утечка, тем дешевле последствия")

1. **Локально:** pre-commit-хук, который ищет в staged-файлах шаблоны ключей.
2. **На push:** *push protection* от GitHub — блокирует push, если в коммите найден известный
   формат секрета (токены GitHub, ключи AWS, приватные ключи и т.д.).
3. **После утечки:** *secret scanning* непрерывно сканирует репозиторий и историю, а по
   партнёрским токенам умеет автоматически сообщать провайдеру о компрометации.

```bash title="Включить проверки (нужны права admin)"
# состояние настроек безопасности
gh api repos/OWNER/REPO --jq '{dependabot: .security_and_analysis.dependabot_security_updates.status,
  secret_scanning: .security_and_analysis.secret_scanning.status,
  push_protection: .security_and_analysis.secret_scanning_push_protection.status}'

# включить
gh api -X PATCH repos/OWNER/REPO -f 'security_and_analysis[secret_scanning][status]=enabled' \
  -f 'security_and_analysis[secret_scanning_push_protection][status]=enabled'
```

```yaml title=".github/workflows/secret-guard.yml — простой собственный барьер"
name: Защита от секретов
on: [push, pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - name: Искать подозрительные строки в диффе
        run: |
          PATTERNS='ghp_[A-Za-z0-9]{36}|github_pat_[A-Za-z0-9_]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----'
          if git diff origin/main...HEAD | grep -E "^\+" | grep -Eq "$PATTERNS"; then
            echo "::error::В изменениях найден секрет. Отзовите его и уберите из коммита."
            exit 1
          fi
          echo "Подозрительных строк не найдено"
```

::: danger Порядок действий при утечке
1. **Отозвать** секрет у провайдера (это важнее всего остального).
2. **Выпустить** новый и обновить там, где он используется (секреты CI, окружения, менеджер паролей).
3. **Оценить** последствия: логи доступа, лимиты, созданные ресурсы.
4. **Очистить** историю (см. следующий урок) — но помните, что после публикации
   она могла быть скопирована: отзыв обязателен независимо от чистки.
5. **Добавить проверку**, чтобы такая утечка не повторилась (push protection, хук, шаблон).
:::

## Права токена GITHUB_TOKEN

```yaml
permissions:
  contents: read          # по умолчанию — только чтение, это правильная база
  pull-requests: write    # если бот комментирует PR
  issues: write           # если создаёт issue
  id-token: write         # если нужен OIDC
```

Правило: **никогда не указывайте `write-all`** и не полагайтесь на старую настройку
«разрешить все права». Токен живёт только во время прогона, но его компрометация
эквивалентна доступу ко всему репозиторию.

## Итоги

- Секреты — для чувствительных значений, переменные — для настроек, `GITHUB_TOKEN` — для самого репозитория.
- Окружения с обязательным одобрением защищают продакшн от случайных деплоев.
- OIDC убирает долгоживущие токены: прогон получает временные креды под свою роль.
- Три уровня защиты от утечек: локальный хук, push protection, secret scanning.
- При утечке первым делом отзываем секрет, только потом занимаемся историей.

::: exercise Упражнение: защитить репозиторий
1. Создайте секрет `DEMO_TOKEN` и переменную `DEFAULT_REGION`; выведите в workflow только
   длину секрета и значение переменной.
2. Настройте окружение `production` с обязательным ревьюером и привяжите его к job деплоя.
3. Включите secret scanning и push protection через `gh api` (или в Settings → Code security).
4. Добавьте workflow `secret-guard.yml` из урока и проверьте его на ветке с «фальшивым»
   ключом вида `AKIAIOSFODNN7EXAMPLE` — job должен упасть.
5. Опишите в три шага, что вы сделаете, если реальный токен всё же попал в `main`.
:::

::: quiz Секрет попал в коммит и был запушен в публичный репозиторий. Что делать первым?
- ( ) Удалить коммит с force-push
- (x) Отозвать/перевыпустить секрет
- ( ) Добавить файл в .gitignore

После публикации значение могло быть скопировано автоматическими сканерами в первые минуты.
Единственная надёжная защита — сделать старый секрет недействительным; очистка истории
вторична и не отменяет отзыв.
:::

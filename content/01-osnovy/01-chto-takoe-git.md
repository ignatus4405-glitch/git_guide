## Проблема, которую решает Git

Пока проект состоит из одного файла, история версий выглядит так:

```bash title="Знакомая картина"
доклад.docx
доклад_финал.docx
доклад_финал_правки.docx
доклад_финал_правки_окончательно_2.docx
```

Это ручное версионирование. Оно ломается сразу, как только над файлами работают
два человека: непонятно, чья версия новее, что именно изменилось и зачем. Что делать,
если через месяц нужно узнать, почему в конфигурации появилась строка, которая ломает
прод? Копия файла ответа не даёт — она хранит состояние, но не объяснение.

**Система контроля версий (VCS)** хранит историю изменений проекта и позволяет:

| Задача | Ответ Git |
| --- | --- |
| Что изменилось с прошлого раза? | `git diff`, `git status` |
| Кто и зачем это изменил? | `git log`, `git blame`, `git show` |
| Вернуться к рабочему состоянию | `git revert`, `git checkout <старый-коммит>` |
| Работать параллельно над двумя задачами | ветки |
| Публиковать и обсуждать изменения | удалённый репозиторий + Pull Request |

## Распределённый Git: у каждого — полная копия

Исторически были централизованные системы (SVN, CVS): один сервер хранил историю, и без
сети работать было нельзя. Git появился в 2005 году как **распределённая** система: при
клоне вы получаете не только последнюю версию файлов, но и всю историю проекта целиком.

![Схема: три «дерева» Git, область подготовки и удалённый репозиторий](assets/img/diagrams/three-trees.svg "Рабочий каталог → область подготовки → локальный репозиторий → GitHub")

Из этого следуют важные практические свойства:

- **Коммиты делаются локально и мгновенно.** Нет сети — не проблема: коммит всё равно создастся.
- **История полная у всех.** Вы можете посмотреть, что менялось в любой ветке, даже если сервер недоступен.
- **GitHub — не Git.** Это хостинг: веб-интерфейс, обсуждения, ревью, CI, права доступа. Git работает и без GitHub, GitHub без Git не существовал бы вовсе.

::: info Что хранит коммит
Коммит в Git — это **снимок дерева проекта** плюс метаданные: автор, дата, сообщение,
ссылка на предыдущий коммит. История — это цепочка снимков, поэтому Git умеет очень быстро
переключаться между версиями, не «переигрывая» изменения по одному.
:::

## Коммит — снимок, а не патч

Это главное отличие модели Git, и оно объясняет почти все дальнейшие команды.

- Файл `README.md` хранится не как «изменение относительно предыдущей версии», а как объект со своим содержимым. Если два коммита содержат одинаковый файл, он хранится один раз — экономия на диске.
- Переключение ветки меняет файлы в рабочем каталоге, но не трогает историю.
- Разветвление и слияние — операции над указателями, а не «копирование кода».

Дополнительно: Git считает хеш содержимого (SHA) — если изменить что угодно внутри коммита,
изменится и его идентификатор. Это делает историю проверяемой: `git fsck` умеет находить
повреждённые объекты.

![Схема: устройство коммита и его связей](assets/img/diagrams/commit-internals.svg "Коммит ссылается на дерево, дерево — на блобы файлов, коммит — на родителя")

## Где здесь GitHub

GitHub добавляет к Git три вещи, без которых невозможна командная работа:

1. **Общая точка правды.** Ваш `push` публикует коммиты, коллега видит их сразу.
2. **Ревью.** Изменения попадают в основную ветку через Pull Request: обсуждение, проверки, апрувы.
3. **Автоматизация.** GitHub Actions запускает тесты, сборки и публикации по событиям репозитория.

::: warning Чего Git не делает
Git не заменяет ни резервное копирование, ни управление зависимостями, ни систему сборки.
Он хранит ровно одно: историю изменений исходников. Всё остальное — инструменты вокруг.
:::

## Итоги

- Git — распределённая система контроля версий: история есть у каждого, коммиты локальны.
- Коммит — снимок проекта с метаданными и ссылкой на родителя, а не набор диффов.
- GitHub — хостинг и социальный слой поверх Git: репозитории, ревью, Actions, права.

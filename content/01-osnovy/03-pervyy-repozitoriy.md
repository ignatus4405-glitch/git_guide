## Создаём репозиторий

```bash title="Новый проект"
mkdir hello-git && cd hello-git
git init                      # создаёт каталог .git — это и есть репозиторий
git status                    # On branch main, No commits yet
```

Каталог `.git` — сердце репозитория: там объекты, ссылки и настройки. Удалить его означает
«перестать быть репозиторием» (файлы останутся), а скопировать `.git` целиком — перенести
всю историю.

Создайте файл и посмотрите, что скажет Git:

```bash title="Первый файл"
printf 'Привет, Git!\n' > README.md
git status
```

```text title="Вывод git status"
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
```

**Untracked** — файл существует, но Git за ним не следит. Прежде чем попасть в историю,
файл проходит область подготовки.

## Три «дерева» Git

![Схема трёх деревьев: рабочая копия, индекс, репозиторий](assets/img/diagrams/three-trees.svg "Как файл перемещается от правки до коммита")

| Область | Что это | Команда, которая сюда перемещает файл |
| --- | --- | --- |
| Рабочий каталог (working tree) | реальные файлы на диске | редактируете в редакторе |
| Область подготовки (index, staging) | черновик следующего коммита | `git add` |
| Репозиторий (`.git`) | зафиксированные снимки | `git commit` |

Смысл двухшагового процесса: вы **собираете** коммит из нужных изменений, а не отправляете
в историю всё, что случайно оказалось изменено в каталоге.

```bash title="Первый коммит"
git add README.md              # файл ушёл в область подготовки
git status                     # Changes to be committed: new file: README.md
git commit -m "docs: добавить приветствие проекта"
git log --oneline              # 8f3c1a2 (HEAD -> main) docs: добавить приветствие проекта
```

::: tip Разница между git add и git commit
`git add` отвечает на вопрос «что попадёт в снимок», `git commit` — «зафиксируйте этот снимок».
Поэтому можно добавить один файл, поправить другой и закоммитить только первый — так коммиты
и остаются логически цельными.
:::

## Пять команд на каждый день

```bash title="Рабочий цикл"
git status                     # что изменилось и что уже подготовлено
git diff                       # построчные правки рабочей копии против индекса
git diff --staged              # построчные правки индекса против последнего коммита
git add -p                     # добавлять изменения кусками (по хункам)
git commit -m "тип: что и зачем"   # зафиксировать снимок
```

`git add -p` — самый недооценённый инструмент новичка: он позволяет разделить «сделал
фичу» и «поправил форматирование» на два коммита, даже если вы меняли файл один раз.

## Хорошее сообщение коммита

Сообщение — часть истории, по нему потом искать причину бага. Формат, который прижился
в сообществах (Conventional Commits):

```text title="Структура"
<тип>: <кратко, до 72 символов>

Зачем это изменение, если из кода это неочевидно.
Ссылка на задачу: Closes #42
```

| Тип | Когда использовать |
| --- | --- |
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | только документация |
| `refactor` | переустройство кода без изменения поведения |
| `test` | тесты |
| `chore` | сборка, зависимости, служебные файлы |

## .gitignore: что не должно попадать в историю

```bash title=".gitignore"
# зависимости и сборка
node_modules/
site/
__pycache__/

# секреты и локальные настройки
.env
*.local
.idea/
.DS_Store
```

Правила:

- `.gitignore` действует только на неотслеживаемые файлы. Если файл уже в истории,
  добавление в игнор ничего не изменит — нужно `git rm --cached file`;
- секреты не «прячем» игнором: файл уже мог попасть в историю — проверяйте `git log -p -S "ключ"`;
- игнор можно задавать глобально: `git config --global core.excludesFile ~/.gitignore_global`.

## Публикуем на GitHub

```bash title="Два пути"
# вариант 1: репозиторий создаём на GitHub и клонируем
gh repo create hello-git --public --clone
cd hello-git

# вариант 2: репозиторий уже есть локально — подключаем remote
gh repo create hello-git --public --source=. --remote=origin --push
# или вручную:
git remote add origin git@github.com:USER/hello-git.git
git push -u origin main
```

После `push` откройте страницу репозитория: файлы, история, вкладка Actions — всё это
следствие четырёх команд, которые вы только что выполнили.

::: warning Ошибка «failed to push some refs (rejected non-fast-forward)»
Она означает, что в удалённой ветке есть коммиты, которых нет у вас. Сначала `git pull --rebase`,
разберитесь с возможными конфликтами и только потом push. `--force` здесь применяют лишь
к своим личным веткам, и безопаснее — `--force-with-lease`.
:::

## Итоги

- Репозиторий — это каталог `.git`; история складывается из снимков.
- Путь файла в историю: рабочая копия → `git add` → индекс → `git commit` → репозиторий.
- `git status` и `git diff` показывают расхождение между слоями — читайте их перед каждым коммитом.
- `.gitignore` защищает от мусора, но не заменяет защиту секретов.
- Публикация: `git remote add origin ...` и `git push -u origin main`.

::: exercise Упражнение: полный цикл в мини-проекте
1. Создайте каталог `git-practice`, выполните `git init`.
2. Добавьте `README.md` с описанием проекта и коммитом `docs: добавить описание`.
3. Создайте `main.py` с функцией и файл `.gitignore` с строкой `__pycache__/`.
   Закоммитьте их **двумя** разными коммитами (`feat` и `chore`).
4. Измените одну строку в `README.md`, затем `git diff`, затем `git add -p` и закоммитьте.
5. Создайте публичный репозиторий на GitHub и запушьте ветку `main`.
:::

::: quiz Файл `.env` с паролем нечаянно закоммитили. Что нужно сделать в первую очередь?
- ( ) Добавить `.env` в .gitignore и перезаписать файл
- (x) Считать секрет скомпрометированным: отозвать ключ и заменить значение
- ( ) Сделать коммит с удалением файла: истории станет чистée

Удаление файла новым коммитом не убирает значение из истории — его легко найти через
`git log -p`. Поэтому правильный первый шаг — отозвать/заменить секрет, и только потом
заниматься очисткой истории (см. модуль «Безопасность»).
:::

## Удалённый репозиторий — это ещё один набор ссылок

Git не различает «локальные» и «удалённые» коммиты: удалённый репозиторий — просто другой
каталог `.git`, с которым вы обмениваетесь объектами. `origin` — имя по умолчанию для адреса,
откуда вы клонировали.

```bash title="Осмотреться"
git remote -v                       # список адресов
git remote show origin              # ветки, настройки трекинга, что устарело
git branch -vv                      # какие локальные ветки за какой удалённой следят
git ls-remote origin                # список веток и тегов без скачивания
```

## fetch против pull

```bash
git fetch origin            # скачать объекты и обновить origin/* — рабочая копия не меняется
git pull                    # = git fetch + git merge (или rebase) текущей ветки
git pull --rebase           # = git fetch + git rebase
```

| Команда | Что меняет | Когда использовать |
| --- | --- | --- |
| `fetch` | только `origin/*` ссылки и объекты | всегда, когда хотите сначала посмотреть |
| `pull` | ещё и ваши файлы (слияние/перебазирование) | когда уверены, что конфликтов не будет или готовы их решать |
| `pull --ff-only` | только если можно «догнать» без слияния | в скриптах и на CI: неожиданная ситуация лучше падения |
| `push` | удалённую ветку | публикация своих коммитов |

::: tip Профессиональная привычка
Вместо «слепого» `git pull` делайте связку: `git fetch origin && git log HEAD..origin/main --oneline`.
Вы увидите, что именно к вам прилетит, и решите — rebase или merge.
:::

## Трекинг веток

```bash title="Связать локальную ветку с удалённой"
git push -u origin feature/login      # -u запоминает upstream
git switch --track origin/feature/login
git branch -u origin/main             # поменять upstream у существующей ветки
git push -d origin feature/old        # удалить ветку на сервере
```

Если задан `push.autoSetupRemote true`, флаг `-u` больше не нужен: первый `git push` в новой
ветке сам создаст ветку на сервере и настроит трекинг.

## Клонирование, форки и синхронизация

Популярны две модели работы:

| Модель | Как выглядит | Кому подходит |
| --- | --- | --- |
| Общий репозиторий | все пушат в один repo, ветки и PR внутри | команда проекта |
| Форк + PR | вы работаете в своём форке, отправляете PR в исходный проект | опенсорс, внешние контрибьюторы |

![Схема: форк и его синхронизация с upstream](assets/img/diagrams/fork-sync.svg "origin — ваш форк, upstream — исходный проект: pull из upstream, push в origin")

```bash title="Синхронизация форка из терминала"
git remote add upstream https://github.com/OWNER/REPO.git
git fetch upstream
git switch main
git rebase upstream/main          # main форка = копия upstream/main
git push origin main              # при переписывании истории: --force-with-lease
git switch -c feature/new-thing
git push -u origin feature/new-thing
```

::: warning force vs force-with-lease
`git push --force` перезапишет удалённую ветку без проверок — вы можете стереть коммиты коллеги.
`git push --force-with-lease` откажется работать, если на сервере появились чужие коммиты,
которых у вас нет. Второй вариант — единственный допустимый в командной работе.
:::

## Разбираем расхождение

Ситуация: `push` отклонён, потому что в удалённой ветке появились новые коммиты.

```bash title="Диагностика и решение"
git fetch origin
git log --oneline --graph HEAD...origin/main      # кто разошёлся и как
git pull --rebase origin main                     # наложить свои коммиты поверх
# или, если в ветке давно идут слияния:
git merge origin/main
```

Крайний случай — «истории расходятся» при push после rebase:

```bash title="Проверка перед силой"
git log --oneline origin/feature..HEAD            # что уйдёт
git log --oneline HEAD..origin/feature            # что пропадёт с сервера
# только для личных веток:
git push --force-with-lease
```

## Итоги

- Удалённый репозиторий — такой же набор объектов и ссылок; `origin` задаёт имя по умолчанию.
- `fetch` безопасен и не меняет файлы, `pull` — это fetch + merge/rebase.
- Трекинг настраивается `-u`, `--track`, `branch -u` и `push.autoSetupRemote`.
- Форк синхронизируется через `upstream`, а свои изменения уходят в `origin`.
- Для переписанных личных ветвей используйте `--force-with-lease`, не `--force`.

::: exercise Упражнение: разойтись и снова сойтись
1. Склонируйте свой репозиторий в две папки (`repo-a` и `repo-b`) и настройте оба на один remote.
2. В `repo-a` сделайте коммит и запушьте.
3. В `repo-b` сделайте другой коммит по той же ветке (без pull) и попробуйте запушить — увидите отказ.
4. Выполните `git fetch` и разберитесь в выводе `git log --oneline --graph HEAD...origin/main`.
5. Решите расхождение через `git pull --rebase` и запушьте. Убедитесь, что истории сходятся.
:::

::: quiz Что изменится в вашем рабочем каталоге после `git fetch origin`?
- ( ) Файлы обновятся до состояния origin/main
- (x) Ничего: обновятся только ссылки origin/*, файлы не тронутся
- ( ) Git автоматически создаст merge-коммит

`fetch` скачивает объекты и обновляет удалённые ссылки. Ваши файлы и ветки изменятся только
после `merge`/`rebase` — то есть после `git pull`.
:::

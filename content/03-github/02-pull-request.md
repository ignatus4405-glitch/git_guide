## Что такое Pull Request

Pull Request (PR) — это запрос «заберите мои изменения в основную ветку». Технически GitHub
сравнивает две ветки и показывает дифф; социально — открывает обсуждение, проверки и историю
решения. PR существует и в проектах без GitHub (GitLab: Merge Request), но именно на GitHub
родился формат «предложение → ревью → слияние».

![Схема: путь изменения от локальной ветки до main](assets/img/diagrams/remote-and-pr.svg "Ветка → push в origin → Pull Request → ревью → merge в main")

## Полный цикл по шагам

```bash title="1. Подготовка ветки"
git switch main
git pull --rebase
git switch -c fix/empty-response
# правки, коммиты, локальные проверки
git push -u origin fix/empty-response
```

```bash title="2. Создание PR (CLI и веб)"
gh pr create --base main --title "fix: пустой ответ API" --body-file .github/PULL_REQUEST_TEMPLATE.md
gh pr create --draft            # черновик: ревью пока не нужно, но CI уже бежит
# в веб-интерфейсе: «Compare & pull request» → выбрать base/compare → описать изменения
```

```bash title="3. Работа с ревью"
gh pr checks                    # статус проверок CI
gh pr view --web                # открыть PR в браузере
gh pr diff                      # дифф в терминале
# правки после замечаний:
git commit -am "refactor: учесть замечания ревью"
git push                        # PR обновится автоматически
```

```bash title="4. Слияние и уборка"
gh pr merge --squash --delete-branch
git switch main && git pull --rebase
git branch -d fix/empty-response
```

## Что писать в описании

Хорошее описание экономит ревьюеру 10–20 минут. Шаблон, который работает:

```markdown title=".github/PULL_REQUEST_TEMPLATE.md"
## Что сделано
Кратко: какая задача решается и как.

## Зачем
Ссылка на задачу: Closes #123

## Как проверено
- [ ] Локально: `python3 build.py && python3 tools/validate.py`
- [ ] Добавлены/обновлены тесты
- [ ] Обновлена документация

## Скриншоты / примеры вывода
(для интерфейсных изменений)
```

::: tip Маленький PR — быстрый review
Практическое правило: PR, который можно прочитать за 10–15 минут, ревьюится в тот же день.
Если диff больше ~400 строк, лучше разбить задачу на части — это ускоряет и ревью, и откат.
:::

## Связь с задачами

В описании или сообщениях коммитов работают ключевые слова, автоматически закрывающие issue
после слияния PR в основную ветку:

| Ключевое слово | Эффект |
| --- | --- |
| `Closes #42` | issue закроется при слиянии |
| `Fixes #42` | то же самое |
| `Refs #42` | просто ссылка, issue останется открытой |

## Стратегии слияния

![Схема: сравнение моделей ветвления](assets/img/diagrams/workflows-compare.svg "GitHub Flow, Git Flow и trunk-based: у каждой модели свои правила")

| Стратегия | Что происходит с историей | Когда выбирать |
| --- | --- | --- |
| Merge commit (`--merge`) | Все коммиты PR + merge-коммит | когда важна хронология работы и ветвление |
| Squash (`--squash`) | Один коммит с сообщением PR | короткие ветки, «шумные» коммиты |
| Rebase (`--rebase`) | Коммиты переприменяются линейно, без merge-коммита | команды с требованием линейной истории |

Выбранная стратегия фиксируется в настройках репозитория и влияет на `git log` для всех.
Поэтому это решение команды, а не личный вкус.

## После слияния

- **Обновите локальную ветку:** `git switch main && git pull --rebase`.
- **Удалите отработанную ветку:** локально (`git branch -d`) и на сервере (`git push -d origin <branch>` или автоматически при merge).
- **Проверьте main:** если включён CI, убедитесь, что сборка после merge зелёная.
- **Не переиспользуйте ветку.** Правки в уже слитую ветку попадут в следующий PR неожиданным образом:
  создайте новую от свежего `main`.

::: warning Черновик вместо незаконченного PR
Не открывайте PR «на половине» без пометки: ревьюеры получат уведомление и потратят время.
Используйте `--draft` (`gh pr ready` снимает пометку) — CI при этом уже работает.
:::

## Итоги

- PR — основной механизм обсуждения и ревью изменений перед слиянием.
- Полный цикл: ветка → push → PR → ревью → merge → синхронизация локального `main`.
- Хороший PR: маленький, с описанием, тестами и ссылкой на задачу.
- Стратегия слияния (merge/squash/rebase) — решение команды, зафиксированное в настройках.
- После merge ветка не переиспользуется.

::: exercise Упражнение: PR от начала до конца
1. В своём репозитории создайте ветку `docs/fix-typo` и поправьте одну строку в README.
2. Запушьте ветку и создайте PR с описанием из трёх разделов: что, зачем, как проверено.
3. Создайте второй коммит после открытия PR и убедитесь, что изменения появились в PR.
4. Проверьте статус проверок (`gh pr checks`), затем слейте PR через squash и удалите ветку.
5. Обновите локальный `main` и убедитесь, что история линейная: `git log --oneline -5`.
:::

::: quiz Ревьюер просит правки, PR ещё не слит. Как отправить изменения?
- ( ) Закрыть PR, создать новую ветку и новый PR
- (x) Дописать коммиты в ту же ветку и сделать push — PR обновится сам
- ( ) Сделать force-push в main

PR всегда показывает состояние ветки-источника на сервере: достаточно закоммитить и запушить
в ту же ветку. Force-push в основную ветку — путь к разрушению чужой работы.
:::

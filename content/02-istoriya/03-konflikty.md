## Почему конфликт — это нормально

Git сливает построчно и только тогда, когда изменения **пересекаются**. Если один разработчик
поправил функцию, а другой — её документацию, конфликта не будет. Конфликт возникает, когда
обе ветки изменили одну и ту же строку или одну и ту же область файла.

![Схема: конфликт слияния и маркеры в файле](assets/img/diagrams/conflict-resolution.svg "Обе ветки изменили одну строку — Git оставляет выбор человеку")

Git сознательно не угадывает: автоматически выбранная версия могла бы молча удалить чужую работу.

## Что появляется в файле

```python title="currency.py — результат незавершённого слияния"
def get_rate():
<<<<<<< HEAD                       # ваша версия (текущая ветка)
    return fetch_rate("EUR", ttl=60)
=======                            # разделитель
    return cached_rate("EUR", ttl=3600)
>>>>>>> feature/cache               # версия вливаемой ветки
```

Порядок работы:

```bash title="Порядок разрешения"
git status                     # список конфликтующих файлов
cat currency.py                # читаем маркеры и решаем, что должно остаться
# правим файл вручную: удаляем маркеры, оставляем одну (или гибридную) версию
git add currency.py            # «конфликт решён»
git status                     # All conflicts fixed but you are still merging
git commit                     # завершаем merge (сообщение уже заготовлено)
# если стало хуже:
git merge --abort
```

::: tip Как выбирать стороны быстро
`git checkout --ours <файл>` — оставить версию своей ветки целиком;
`git checkout --theirs <файл>` — версию вливаемой.
Внутри rebase смысл меняется местами: «ours» — это уже перебазированная ветка, а «theirs» —
коммит, который применяется. Сомневаетесь — посмотрите `git status` и `git log --merge`.
:::

## Конфликты в трёх местах

Конфликты встречаются не только в обычном `merge`:

| Ситуация | Что делать |
| --- | --- |
| `git merge` | решить конфликт → `git add` → `git commit` |
| `git rebase` / `git pull --rebase` | решить → `git add` → `git rebase --continue` (или `--skip`, `--abort`) |
| `git cherry-pick` | решить → `git add` → `git cherry-pick --continue` |
| `git stash pop` | решить → `git add` → обычно просто продолжаете работу |

```bash title="Инструменты в помощь"
git mergetool                 # откроет настроенный графический инструмент (Code, meld, kdiff3)
git diff --name-only --diff-filter=U      # только конфликтующие файлы
git checkout --merge <файл>   # вернуть файл в состояние с маркерами конфликта
git rerere status             # что помнит «переиспользование решения»
```

## rerere: не решать одно и то же дважды

`rerere` (reuse recorded resolution) запоминает, как вы разрешили конфликт, и применяет то же
решение, если такой же конфликт встретится снова. Особенно полезно при длинных `rebase`
и при повторяющихся слияниях из основной ветки.

```bash title="Включить один раз"
git config --global rerere.enabled true
git config --global rerere.autoupdate true   # сразу помечать разрешённые файлы как staged
```

## Стратегия, которая экономит часы

1. **Сначала обновляйтесь, потом правьте.** Перед началом работы: `git switch main && git pull --rebase`.
2. **Синхронизируйтесь часто.** Маленькие слияния редко дают сложные конфликты.
3. **Разделяйте ответственность за файлы.** Один файл — один владелец в момент правок;
   для этого есть `CODEOWNERS` (см. модуль «Командная работа»).
4. **Не смешивайте форматирование и логику.** Массовое переформатирование в одном коммите
   с логикой гарантирует конфликты у всех.
5. **Проверяйте после разрешения.** Прогоните тесты и сборку — конфликт мог «сойтись» синтаксически,
   но сломать поведение.

::: warning Опасный антипаттерн
Разрешать конфликт командой `git checkout --ours .` для всего проекта «чтобы быстрее».
Это молча удаляет чужие изменения, и никто не узнает об этом до следующего релиза.
:::

## Итоги

- Конфликт возникает только при пересечении правок и всегда требует решения человека.
- Маркеры `<<<<<<<`, `=======`, `>>>>>>>` показывают две версии; их нужно свести в одну осмысленную.
- `git status` ведёт по шагам; `--abort` возвращает всё назад.
- `rerere` автоматизирует повторяющиеся решения, `mergetool` ускоряет ручную работу.
- После любого конфликта обязательны тесты: синтаксис и смысл — разные вещи.

::: exercise Упражнение: конфликт своими руками
1. Создайте репозиторий с файлом `app.py`, содержащим строку-конфигурацию.
2. В ветке `feature/a` измените эту строку и закоммитьте.
3. Вернитесь в `main`, измените **ту же** строку по-другому и тоже закоммитьте.
4. Выполните `git merge feature/a` и посмотрите маркеры конфликта.
5. Разрешите конфликт так, чтобы сохранить смысл обеих правок (например, объединив параметры).
6. Отмените всё (`git merge --abort` до коммита) и попробуйте вариант с `git checkout --ours`.
   Сравните результаты и объясните разницу.
:::

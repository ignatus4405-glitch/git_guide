## Ветка — это метка, а не копия каталога

В отличие от многих систем, ветка в Git не копирует файлы. Это файл в `.git/refs/heads/`,
в котором лежит SHA одного коммита. Когда вы делаете коммит, метка автоматически сдвигается
вперёд. Отсюда мгновенное создание веток и дешёвые эксперименты.

![Схема: ветвление и слияние коммитов](assets/img/diagrams/branches-merge.svg "main и feature расходятся в точке ветвления и сходятся в merge-коммите")

```bash title="Работа с ветками"
git switch -c feature/login     # создать ветку и перейти в неё
git switch main                 # вернуться в main
git switch -                    # вернуться в предыдущую ветку (как cd -)
git branch                      # список локальных веток
git branch -vv                  # + какой коммит и какой upstream
git branch -d feature/login     # удалить слитую ветку
git branch -D feature/old       # удалить принудительно (коммиты потеряются)
git push -u origin feature/login
```

```bash title="Переименование основной ветки"
git branch -m master main       # локально
git push origin -u main         # опубликовать
# затем в GitHub: Settings → Branches → Default branch → main
```

::: note Почему switch, а не checkout
`git checkout` делает слишком много: переключает ветки, восстанавливает файлы, создаёт ветки.
С версии 2.23 добавили две явные команды: `git switch` (ветки) и `git restore` (файлы).
Так безопаснее: невозможно случайно потерять правки, перепутав режимы.
:::

## Слияние: fast-forward и merge-коммит

```bash title="Слияние ветки"
git switch main
git merge feature/login
```

Возможны два сценария.

| Сценарий | Когда | Что происходит |
| --- | --- | --- |
| Fast-forward | `main` не менялся с момента ветвления | указатель `main` просто переезжает на коммит feature, нового коммита нет |
| Merge-коммит | `main` ушёл вперёд | создаётся коммит с двумя родителями и сообщением `Merge branch ...` |

Полезные режимы:

```bash title="Управление слиянием"
git merge --no-ff feature/login    # принудительно создать merge-коммит (видно в истории)
git merge --squash feature/login   # склеить все коммиты ветки в один, но без связи с веткой
git merge --abort                  # отменить начатое слияние и вернуть состояние до него
git merge --continue               # продолжить после разрешения конфликтов
```

::: tip Правило выбора
`--no-ff` полезен, когда важно видеть в истории целые «пласты» работ (фича целиком).
Fast-forward оставляют по умолчанию для коротких веток, а `--squash` часто ставят как
стратегию слияния PR, чтобы в основной ветке не было «fix typo» по десять раз.
:::

## Что такое конфликт и когда он не возникает

Git сливает изменения автоматически, если правки не пересекаются: разные файлы или разные
строки одного файла. Конфликт появляется, когда обе ветки изменили одну и ту же часть файла.

```bash title="Порядок действий при конфликте"
git status                 # отмечены файлы: both modified / unmerged
# правите файлы, выбирая итоговое содержимое
git add <файл>             # отметить как разрешённый
git commit                 # завершить слияние
```

Подробно конфликты разбираются в следующем уроке — здесь важно запомнить, что
`git merge --abort` всегда возвращает вас в состояние до начала слияния.

## Типичные схемы работы

```bash title="Ветка под задачу"
git switch main && git pull --rebase
git switch -c fix/typo-in-docs
# … правки, коммиты …
git push -u origin fix/typo-in-docs   # дальше — Pull Request
```

```bash title="Проверить чужую ветку локально"
git fetch origin
git switch --track origin/feature/payments
# или разово, без создания локальной ветки:
git switch --detach origin/feature/payments
```

::: warning Не храните долгие ветки
Чем дольше ветка живёт отдельно, тем больше расхождений и тем болезненнее слияние.
Ориентир из практики: ветка должна жить дни, а не месяцы. Не сработало — разбейте задачу.
:::

## Итоги

- Ветка — подвижная метка на коммит; создание и переключение стоят почти ничего.
- `git switch` для веток, `git restore` для файлов — современная замена `git checkout`.
- Слияние бывает fast-forward (без нового коммита) и merge-коммитом (с двумя родителями).
- `--no-ff`, `--squash`, `--abort` и `--continue` управляют слиянием.
- Ветки удаляются легко: `-d` только если слита, `-D` — принудительно.

::: exercise Упражнение: две ветки, одно слияние
1. Создайте репозиторий, сделайте два коммита в `main`.
2. Создайте ветку `feature/a`, добавьте файл и сделайте коммит.
3. Вернитесь в `main`, добавьте изменений в другой файл и закоммитьте.
4. Слейте `feature/a` в `main` через `git merge --no-ff` и посмотрите результат
   в `git log --oneline --graph`.
5. Повторите сценарий, но перед слиянием верните `main` назад (`git reset --hard HEAD~1`)
   так, чтобы слияние прошло fast-forward. Сравните истории.
:::

::: quiz Чем fast-forward отличается от обычного слияния?
- ( ) Fast-forward создаёт отдельный коммит-слияние, а обычное — нет
- (x) Fast-forward просто переносит указатель ветки, не создавая нового коммита
- ( ) Fast-forward возможен только при наличии конфликтов

Fast-forward возможен, когда целевая ветка не разошлась с текущей: указатель просто
переезжает вперёд. Если в целевой ветке появились свои коммиты — Git создаёт merge-коммит
с двумя родителями.
:::

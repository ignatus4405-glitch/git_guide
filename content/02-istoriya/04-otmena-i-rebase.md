## merge или rebase: две философии одной истории

![Схема: сравнение merge и rebase](assets/img/diagrams/merge-vs-rebase.svg "merge сохраняет ветвление, rebase выпрямляет историю, переписывая коммиты")

```bash title="Оба варианта"
git switch feature/login
git merge main            # ветка сольётся: появится merge-коммит
git rebase main           # коммиты ветки переприменятся поверх main (новые SHA)
```

| Критерий | merge | rebase |
| --- | --- | --- |
| История | сохраняет ветвление как было | линейная, «выпрямленная» |
| SHA коммитов | не меняются | меняются у всех переприменённых |
| Безопасность для общих ветвей | безопасен | опасен: переписывает историю |
| Читаемость диффа | merge-коммиты шумят | удобно читать и искать `bisect` |
| Конфликты | решаются один раз | могут повториться на каждом коммите |

**Правило:** перебазируйте только те коммиты, которые ещё никто не забрал к себе.
Личные ветки — rebase, общие (`main`, `release/*`) — merge.

## Интерактивный rebase: чистка перед ревью

```bash title="git rebase -i HEAD~4"
pick   a1b2c3d feat: добавить форму поиска
squash d4e5f60 fix: опечатка
squash 7g8h9i0 fix: ещё опечатка
reword j1k2l3m feat: добавить валидацию
```

Доступные команды: `pick`, `reword` (изменить сообщение), `edit` (остановиться и поправить),
`squash` (склеить с предыдущим), `fixup` (склеить, выбросив сообщение), `drop` (удалить коммит),
`exec` (выполнить команду после коммита).

```bash title="Порядок и адресация"
git rebase -i HEAD~3            # три последних коммита
git rebase -i origin/main       # все свои коммиты поверх origin/main
git rebase --continue           # после разрешения конфликта
git rebase --skip               # пропустить проблемный коммит
git rebase --abort              # вернуть всё как было
```

::: warning Опасность одного флага
`git rebase --onto` и `-i` вместе позволяют «вырезать» куски истории. Это мощно и необратимо
для коллег, если ветка уже опубликована. Перед силой — `git branch backup/feature` и push ветки-бэкапа.
:::

## Четыре уровня отмены

![Схема: restore, reset и revert](assets/img/diagrams/reset-vs-revert.svg "Выбирайте инструмент отмены по уровню: рабочая копия, локальная история, публичная история")

```bash title="Уровень 1: рабочая копия"
git restore file.py                  # выбросить правки в файле
git restore --staged file.py         # убрать файл из индекса, оставив правки
git clean -n                         # показать неотслеживаемые файлы (пробный прогон)
git clean -fd                        # удалить их (осторожно!)
```

```bash title="Уровень 2: локальная история"
git commit --amend -m "новое сообщение"    # поправить последний коммит
git reset --soft HEAD~1                    # убрать коммит, оставив изменения в индексе
git reset --mixed HEAD~1                   # убрать коммит и из индекса (по умолчанию)
git reset --hard HEAD~1                    # уничтожить коммит и правки (!)
```

```bash title="Уровень 3: публичная история"
git revert <sha>                  # создать коммит, отменяющий изменения указанного
git revert -m 1 <merge-sha>       # отменить merge-коммит, оставив первого родителя
git push                          # revert безопасен для уже опубликованных ветвей
```

```bash title="Уровень 4: спасение"
git reflog                        # журнал перемещений HEAD
git switch -c rescue <sha-из-reflog>
git fsck --lost-found             # найти «висячие» объекты
```

## stash: отложить незаконченное

```bash title="Временное хранилище"
git stash push -m "черновик поиска"   # отложить текущие правки
git stash list                        # список отложенного
git stash pop                         # вернуть и удалить из стека
git stash apply stash@{1}             # вернуть, оставив в стеке
git stash drop                        # удалить запись
git stash branch feature/from-stash   # развернуть правки в новую ветку
```

::: tip git stash в 2026 году
Для незаконченной работы часто удобнее `git worktree add ../feature-x feature/x`: вы получаете
второй рабочий каталог на той же истории и не откладываете правки вовсе. `stash` остаётся
удобным для быстрых переключений «на пять минут».
:::

## Итоги

- merge сохраняет историю, rebase её выпрямляет и переписывает SHA — решайте по ветке.
- Интерактивный rebase — стандартный способ привести черновик к аккуратному PR.
- Уровни отмены: `restore` (файлы) → `reset` (локальная история) → `revert` (публичная).
- `git reflog` спасает почти всё, что потерялось из-за `reset` или неудачного rebase.
- `stash` и `worktree` помогают переключаться между задачами без потери работы.

::: exercise Упражнение: отменить, не потеряв
1. Сделайте три коммита в ветке. Поправьте средний по смыслу: `git rebase -i HEAD~3` со `squash` и `reword`.
2. Сломайте состояние: `git reset --hard HEAD~2`. Убедитесь, что коммиты пропали из `git log`.
3. Восстановите их через `git reflog` и новую ветку.
4. Создайте «плохой» коммит и отмените его через `git revert`, затем сравните `git log` до и после.
5. Сформулируйте правило: для каких ветвей вы будете использовать `reset`, а для каких только `revert`.
:::

::: quiz В ветке `main`, которая уже опубликована, нужно отменить один коммит. Что выбрать?
- ( ) git reset --hard HEAD~1
- ( ) git rebase -i и drop этого коммита
- (x) git revert <sha>

`reset` и `rebase` переписывают историю: у коллег останутся другие SHA, и им придётся разбираться
с расхождением. `revert` создаёт новый коммит-отмену и безопасен для общих ветвей.
:::
